## 1. 引言

- 单卡推理的两个瓶颈：decode 受**显存带宽**，并发受**显存容量**。
- 本文把 vLLM 相对 HF 的吞吐优势拆成四项机制：连续批处理、分页 KV、前缀共享、量化。
- 贡献：同硬件同负载的实测数据 + 可复现脚本 + 归因拆解（而非"调包对比"）。

## 2. 背景与机制

### 2.1 prefill 与 decode

- **prefill**：整段输入并行计算，受算力限制（compute-bound），决定 TTFT。
- **decode**：逐 token 串行生成，每步都要把全部权重从显存读一遍，受带宽限制
  （memory-bandwidth-bound），决定 TPOT。
- 理论值：权重 5.79 GiB ÷ 320 GB/s ≈ 18 ms/token ≈ **55 tok/s**（单请求 decode 上限）。

### 2.2 KV cache

- 缓存历史 K/V 避免重算，代价是显存；占用 ∝ 并发 × 序列长度。
- KV cache 挤占显存 → 限制 batch → 限制吞吐，是 2.3/2.4 两节机制存在的理由。

### 2.3 连续批处理（Orca）

- 内容见 `docs/notes_orca.md`；配一张"request-level vs iteration-level 调度"示意图。
- 一句话：调度粒度从请求缩到迭代，完成的立即返回、新到的立即插入。

### 2.4 分页 KV（vLLM）

- 内容见 `docs/notes_vllm.md`；配一张 block table 示意图（逻辑块 → 物理块）。
- 一句话：KV 显存按固定大小 block 管理，碎片 < 4%，支持跨请求共享。

### 2.5 量化（AWQ）

- Int4 权重量化，显存约减半。
- 收益路径是**显存 → 更大的 KV 池 → 更高并发**，而非算力提升。
- T4 实测：吞吐 381 → 368 tok/s（−3.4%），并发上限 41.73× → 69.02×；
  峰值显存 11.99 → 12.03 GB 几乎不变（vLLM 预分配），**不能用峰值显存作证据**。

## 4. E1 结果

- 图：`figs/throughput.png`、`figs/memory.png`
- 中位数表（tok/s；括号内为峰值显存 GB）：

| batch | HF | vLLM | 倍数 |
|---|---|---|---|
| 1 | 22.38 (5.84) | 32.99 (11.72) | 1.5× |
| 2 | 42.09 (5.92) | 61.52 (11.76) | 1.5× |
| 4 | 66.85 (6.08) | 112.01 (11.83) | 1.7× |
| 8 | 91.64 (6.40) | 187.71 (11.99) | 2.0× |
| 16 | 113.36 (7.04) | 291.39 (11.99) | 2.6× |

- 结论：
  - batch=1 两者差距小（都受带宽限制）；
  - batch≥4 起 vLLM 明显拉开（连续批 + 分页生效）；
  - HF 显存随 batch 线性涨；vLLM 被 KV 池上限顶住。
- 与理论上限对比：HF batch=1 实测 22.38 tok/s ≈ 55 tok/s 的 **41%**。

## 6. E3 权衡

- 图：`figs/tradeoff.png`（轻载）、`figs/tradeoff_overload.png`（过载），
  `load_client.py` 产出 p99_e2e_ms。
- **结论：拐点位置取决于负载强度，不存在固定的"单卡最优配置"。**

| 工况 | k 范围 | 吞吐 tok/s | TTFT（k=32） | E2E p99（k=32） |
|---|---|---|---|---|
| 轻载 4 req/s / 32 条 | 1→32 | 33.39 → 308.92 | 0.17 s | 9.74 s |
| 过载 16 req/s / 64 条 | 4→32 | 114.85 → 393.71 | 5.89 s | 18.73 s |

  - 轻载：无拐点，k=32 全面最优（吞吐最高、TTFT 最低、E2E p99 与 k=16 持平）；
  - 过载：边际增益 +69% → +54% → +32% 递减，k∈[1,32] 内未见饱和；
    外推饱和点接近 **FP16 KV 池上限 41.7×**（若换 AWQ，上限提到 69×）。
- 报告里给"配置—负载"二维结论，而不是一个数字。

> 口径：41.7× / 69× 是启动日志按 **4096 token/请求**给的并发上限；E3 请求约 640 token
> （512+128），实际可容纳并发更高，饱和点数字只作量级参考。

## 7. 讨论

- 与 vLLM / Orca 论文的趋势是否一致；差异的可能原因。
- T4 不支持 FlashAttention-2 → 自动降级 XFormers，对绝对值的影响。
- V0 引擎（`VLLM_USE_V1=0`）与新版引擎的调度/分页机制相同，不影响趋势结论。

## 8. 局限

- 单卡、合成负载、T4 较老、未做 kernel 级优化、AWQ 精度未评测。
- **前缀共享不可测**：`OutOfResources: shared memory, Required: 98304, limit 65536`；
  T4（sm75）每 SM 只有 64 KB，该 kernel 要 96 KB，硬件限制无解，不能与其余三项并列比较。
- **量化收益不可用峰值显存衡量**：vLLM 按 `gpu_mem_util` 预分配，FP16/AWQ 峰值接近；
  应看并发上限（41.73× → 69.02×）。
- E1 与 E2-a 的请求条数不同（16 vs 32），递进链条不是严格单变量消融。
- E3b 过载工况只跑了 1 次（无中位数），趋势可读但绝对值有抖动。

## 9. 结论（三条，须能指到具体数据行）

1. 单卡 decode 受带宽限制，HF batch=1 实测 22.38 tok/s ≈ 理论上限 55 tok/s 的 41%。
2. vLLM 的增益几乎全部来自连续批处理（27.69 → 372.66 tok/s，13.5×）；
   显存利用率贡献 ≈ 0，Int4 量化吞吐 −3.4%、但把并发上限从 41.73× 提到 69.02×。
3. 不存在固定最优配置：轻载 k=32 全面最优；过载时边际增益递减，
   饱和点接近 FP16 KV 池上限 41.7×（AWQ 为 69×）。
