# 单卡 LLM 推理的性能 Profiling 与归因分析

> 状态：初稿（C 起草，待组长审）。数据来自 `results.csv`（66 行，T4 实机），
> 所有数字为组内重复实验的中位数；重复次数见 §3.4。
> 图见 `figs/`；正文中 `图 x` 对应文件名已标注。

## 摘要

本文在同一台 Tesla T4（16 GB）上，以 HuggingFace `generate` 为基线、vLLM 为优化侧，
用同一份合成负载测量 LLM 推理的吞吐、延迟与显存，并把 vLLM 的吞吐优势拆解到具体机制上。
66 次实测的主要发现是：（1）HF 与 vLLM 的差距随并发从 1.5× 扩大到 2.6×；
（2）连续批处理是几乎全部增益的来源——固定 32 条请求时，`max_num_seqs` 从 1 提到 32，
吞吐从 27.69 涨到 372.66 tok/s（13.5×）；（3）显存利用率调参在本负载下贡献≈0，
前缀共享因 T4 共享内存不足无法测量；（4）Int4 量化的 token 吞吐反而降 3.4%，
但它把满长并发上限从 41.73× 提到 69.02×——量化的收益是显存容量，不是单 token 速度；
（5）吞吐-延迟的拐点取决于到达速率，不存在固定的"单卡最优配置"。

## 1. 引言

LLM 推理分为 prefill 与 decode 两个阶段。prefill 把整段输入并行算完，受算力限制；
decode 逐 token 串行生成，每一步都要把全部模型权重从显存读一遍，受**显存带宽**限制。
单卡部署是最常见也最受约束的形态：显存装不下大 batch，带宽决定了单请求的速度上限。

工业界的推理引擎（vLLM 等）比朴素实现快很多，但"快多少"和"快从哪来"是两个问题。
本文回答三个问题：

- **Q1**：在 T4 上，HF 原生实现与 vLLM 的差距有多大？是否与带宽理论值吻合？
- **Q2**：差距中，连续批处理、分页 KV/显存、前缀共享、量化各贡献多少？
- **Q3**：吞吐与延迟的权衡曲线在哪里拐弯？单卡的最优配置是什么？

与"跑两个引擎、画一根柱状图"的做法不同，本文对每一项机制都配了单变量实验与机制解释，
并在机制之间不可简单相加时，改用"递进链条"呈现系统级增益（§5.6）。

## 2. 背景与机制

### 2.1 prefill 与 decode

- **prefill**：整段输入并行计算，compute-bound，决定首 token 时延（TTFT）。
- **decode**：逐 token 串行，每步把权重读一遍，memory-bandwidth-bound，决定 token 间时延（TPOT）。
- 理论上限：权重 5.79 GiB ÷ 320 GB/s ≈ 18 ms/token ≈ **55 tok/s**（单请求 decode 天花板）。

### 2.2 KV cache

KV cache 缓存历史 K/V 以避免重算，代价是显存。其占用与"并发数 × 序列长度"成正比，
因此 KV cache 越大，能同时服务的请求越少。这直接引出后两节的机制。

### 2.3 连续批处理（Orca, OSDI'22）

传统系统按**请求粒度**组 batch：一个 batch 必须等最长的请求生成完，早完成的请求占着槽位空转，
新请求必须等整批结束。Orca 提出 **iteration-level scheduling**：每一轮迭代重新决定 batch 里有谁，
完成的立即返回、新到的立即插入；配合 selective batching 处理变长序列。
论文在 GPT-3 175B 上报告同延迟下吞吐为 FasterTransformer 的 36.9×（190 ms，0.185 → 6.81 req/s）。

### 2.4 分页 KV（vLLM / PagedAttention, SOSP'23）

已有系统按最大输出长度连续预分配 KV cache，内部/外部碎片会浪费 60–80% 显存。
PagedAttention 把 KV cache 切成固定大小的 block，用 per-request block table 映射逻辑位置到
物理 block（借鉴操作系统虚拟内存），把浪费降到 <4%，并支持块级前缀共享（写时复制）。
论文报告同延迟下吞吐为 FasterTransformer/Orca 的 2–4×。

### 2.5 量化（AWQ, MLSys'24）

AWQ 是 W4A16 权重量化：不是所有权重同等重要，约 0.1%–1% 的**显著通道**对应更大的激活值，
量化误差对输出影响更大。AWQ 用激活统计找这些通道，再用 per-channel scaling 数学等价地
降低其量化误差，不引入混合精度；配套 TinyChat 在桌面/移动 GPU 上比 HF FP16 快 >3×。

> 三个机制并不正交：连续批处理决定"每轮迭代放多少请求"，分页 KV 决定"显存能装多少请求"，
> 量化改变"权重占多少显存、从而给 KV 池留多少"。因此本文同时给出**单变量消融**（§5.2–§5.5）
> 和**递进链条**（§5.6）两种视角，而不是把四项收益强行加总。

## 3. 实验设置

### 3.1 硬件与软件

| 项 | 值 |
|---|---|
| GPU | Tesla T4 16 GB（Turing, sm75；驱动 570.124.04 / CUDA 12.8） |
| 系统 | Ubuntu 22.04.5, Python 3.12.7 |
| 模型 | Qwen2.5-3B-Instruct（FP16，权重 5.79 GiB） |
| 量化模型 | Qwen2.5-3B-Instruct-AWQ（Int4，权重 1.95 GiB） |
| 关键版本 | `vllm==0.10.2` / `torch 2.8.0+cu128` / `transformers==4.55.2` / `numpy 2.2.6` |
| 负载 | 合成 token id，输入 512 / 输出 128，`temperature=0` |

工程约束：容器内 V1 引擎初始化失败，统一用 `VLLM_USE_V1=0`（V0 引擎）；T4 不支持
FlashAttention-2，vLLM 自动降级 XFormers。完整环境快照见 `env.txt`。

### 3.2 负载与实验矩阵

- **E1**：静态批，`batch ∈ {1,2,4,8,16}`，HF 与 vLLM 各跑一遍。
- **E2-a**：固定 32 条请求一次性提交，扫 `max_num_seqs ∈ {1,4,16,32}`。
- **E2-b**：`gpu_memory_utilization ∈ {0.6,0.7,0.9}`。
- **E2-c**：共享 480 token 系统提示 + 32 token 差异，开/关 `enable_prefix_caching`。
- **E2-d**：FP16 vs AWQ-Int4，batch=32。
- **E3**：并发压测，固定到达速率，扫 `max_num_seqs ∈ {1..32}`；轻载 4 req/s×32 条，
  过载 16 req/s×64 条。

> **E1 与 E2-a 的区别**（最容易混淆）：E1 的 `batch` 就是一次提交的请求数，vLLM 一次只看见 B 条；
> E2-a 固定提交 32 条，`max_num_seqs` 才是调度器的并发上限。两者回答的问题不同。

### 3.3 指标定义

| 指标 | 定义 |
|---|---|
| TTFT | 请求发出 → 首 token 返回（ms） |
| TPOT / ITL | 首 token 之后相邻 token 的平均间隔（ms） |
| 吞吐 | 单位时间产出的输出 token 数（tok/s） |
| 峰值显存 | 进程运行期间 `torch.cuda.max_memory_allocated()` 的最大值（GB） |
| P99 | 99% 请求都低于该值，衡量长尾 |

**口径说明**：vLLM 按 `gpu_memory_utilization` **预分配** KV 池，其"峰值显存"接近总占用而非需求，
不能用来比较不同精度的显存需求。

### 3.4 重复与可复现

- 重复次数（按实际数据）：E1 3 次；E2-a/b/d 2 次；E3 轻载 2 次；E3b 过载 1 次。均取中位数。
- 每组正式计时前先 warmup；实验期间独占 GPU（`nvidia-smi` 确认无其他进程）。
- 一键复现：`bash setup.sh` + `bash run_all.sh`；原始数据 `results.csv`（66 行）；
  出图 `python plot.py --exp <E1|E2-a|E2-b|E2-d|E3|E3b>`。

## 4. E1：基线对比

**图 1** `figs/throughput.png`（吞吐 vs batch）；**图 2** `figs/memory.png`（峰值显存 vs batch）。

| batch | HF tok/s | vLLM tok/s | vLLM/HF | HF 峰值 GB | vLLM 峰值 GB |
|---|---|---|---|---|---|
| 1 | 22.38 | 32.99 | 1.5× | 5.84 | 11.72 |
| 2 | 42.09 | 61.52 | 1.5× | 5.92 | 11.76 |
| 4 | 66.85 | 112.01 | 1.7× | 6.08 | 11.83 |
| 8 | 91.64 | 187.71 | 2.0× | 6.40 | 11.99 |
| 16 | 113.36 | 291.39 | 2.6× | 7.04 | 11.99 |

观察：

1. **batch=1 时差距最小**（1.5×）：两者都受单请求带宽限制。HF 22.38 tok/s 约为理论上限
   55 tok/s 的 **41%**，vLLM 32.99 tok/s 约为 **60%**；差距来自 kernel 效率与 attention 实现，
   而不是"批处理"——此时没有并发可批。
2. **差距随并发扩大**（1.5× → 2.6×）：batch≥4 后 vLLM 明显拉开，说明增益来自调度与显存管理，
   而非单请求加速。
3. **显存形态不同**：HF 随 batch 从 5.84 涨到 7.04 GB（线性增长，每条约 0.075 GB）；
   vLLM 从 11.72 到 11.99 GB，基本被预分配的 KV 池顶住——这不是"vLLM 更费显存"，
   而是它把剩余显存提前拿去做 KV 池了。

## 5. E2：归因

### 5.1 为什么放弃"四项占比之和 ≈ 100%"

原计划以 HF 为下界，把四项机制的增量相加。实测后发现该口径不成立：

- 连续批处理的单变量收益是 **13.5×**，量级远超其余三项；
- 显存利用率调参的收益 **≈0**；
- 量化对吞吐是 **负贡献**（−3.4%）；
- 前缀共享在 T4 上**不可测**。

四项不是同一个量纲上的可加项：显存调参与量化主要改变"能装多少并发"，而连续批改变"每轮迭代
实际跑多少请求"，二者耦合。因此本文用两种视角：先做单变量消融（§5.2–§5.5），再用递进链条
给出系统级增益（§5.6）。

### 5.2 E2-a：连续批处理（图 3 `figs/E2_a_sweep.png`）

固定 32 条请求一次性提交，只改调度器的并发上限：

| max_num_seqs | 吞吐 tok/s | 相对 k=1 | 全部完成耗时 s |
|---|---|---|---|
| 1 | 27.69 | 1.0× | 149.08 |
| 4 | 111.23 | 4.0× | 36.82 |
| 16 | 287.47 | 10.4× | 14.25 |
| 32 | 372.66 | 13.5× | 11.00 |

- k=1 时 vLLM 退化为逐请求调度，GPU 在等最长请求，吞吐仅 27.69 tok/s；
- 随 k 增大，完成的请求立即让出槽位、新请求立即插入，吞吐近似线性上升；
- k=16→32 仍有 +29.6%（287.47→372.66），说明 32 条请求下并发上限仍是约束。

> 注意：k=1 的 27.69 与 E1 batch=1 的 32.99 不可直接比较——前者是 32 条请求排队、每次只跑 1 条，
> 后者只提交了 1 条请求，没有排队。

### 5.3 E2-b：显存利用率（图 4 `figs/E2_b_sweep.png`）

| gpu_mem_util | 吞吐 tok/s | 峰值显存 GB |
|---|---|---|
| 0.6 | 305.48 | 7.62 |
| 0.7 | 304.67 | 9.08 |
| 0.9 | 300.31 | 11.99 |

三档吞吐在 300–305 tok/s 内，差异 <2%，**贡献≈0**。

解释：本实验是 batch=16、in=512/out=128 的中等负载，0.6 的显存已经足够装下当前并发，
KV 池不是瓶颈；降低 `gpu_mem_util` 只是减少预分配，不会让吞吐变快（反而略降，可能是
调度/分配开销的抖动）。**这不否定分页 KV 的价值**——它的价值是在高并发/长序列下"装得下、
不浪费"；本负载没有触发显存约束，所以这个旋钮没有发挥空间。

### 5.4 E2-c：前缀共享（T4 不可测）

开启 prefix caching 时，vLLM 的 Triton kernel 报：

```
OutOfResources: shared memory, Required: 98304, limit 65536
```

T4（sm75）每个 SM 只有 64 KB 共享内存，该 kernel 需要 96 KB，属于硬件限制。因此 E2-c
**没有开/关对照数据**，报告中如实标注"不可测"，不能写成"收益为 0"。
`figs/E2_c_compare.png` 只有单侧数据，不作为收益图使用。

### 5.5 E2-d：Int4 量化（图 5 `figs/E2_d_compare.png`）

同为 32 条请求、`gpu_mem_util=0.9`，只换权重：

| 项 | FP16 | AWQ-Int4 | 变化 |
|---|---|---|---|
| 吞吐 tok/s | 381.28 | 368.35 | **−3.4%** |
| 峰值显存 GB | 11.99 | 12.03 | 几乎不变（预分配，不可用） |
| 权重 GiB | 5.79 | 1.95 | −3.84 GiB |
| KV 池 GiB | 5.87 | 9.71 | **+65%** |
| 满长并发上限 | 41.73× | 69.02× | **+65%** |

- 量化的收益**不在 token 吞吐**：T4 上 Int4 的解量化要吃算力，吞吐反而降 3.4%；
- 收益在**容量**：权重省下的 3.84 GiB 全部转成 KV 池，满长并发上限从 41.73× 提到 69.02×；
- 峰值显存完全看不出这个收益（11.99 vs 12.03），必须引用启动日志的
  `Maximum concurrency for 4096 tokens per request`。

这与 AWQ 论文"TinyChat 比 HF FP16 快 >3×"不矛盾：论文的加速来自专用 4-bit kernel，
而本文用的是 vLLM 在 Turing 上的通用路径；两者测的不是同一件事。

### 5.6 E2 递进链条（图 6 `figs/attribution_waterfall.png`）

以 HF 静态批 batch=16 为起点，逐级替换系统：

| 级 | 吞吐 tok/s | 增量 |
|---|---|---|
| HF 静态批 batch=16 | 113.36 | 基线 |
| + vLLM 引擎（kernel + 分页 KV + 调度） | 291.39 | +178.03（2.6×） |
| + 提高并发（16→32 条请求，k=32） | 372.66 | +81.27（较上一级 +27.9%） |

解释：

- 第一级 2.6× 是 vLLM 引擎的整体替换，**同时包含** kernel 优化、分页 KV 与连续批处理
  （batch=16 的 vLLM 已经在批处理 16 条请求），无法再拆开；
- 第二级 +27.9% 是"并发上限从 16 提到 32"的边际收益。它不是"从 0 开启连续批"，
  所以不能标成 13.5×——13.5× 是 k=1→32 的单变量消融（§5.2），两者基线不同；
- 整条链从 113.36 到 372.66，系统级提升 **3.3×**。

> 口径注意：第一级用 E1（16 条请求），第二级用 E2-a（32 条请求），两级负载条数不同；
> 这是"各自配置下递进"的展示，不是严格方差分解。汇报与答辩时应如实说明。

## 6. E3：吞吐-延迟权衡

**图 7** `figs/tradeoff.png`（轻载）；**图 8** `figs/tradeoff_overload.png`（过载）。
用 `load_client.py` 按固定到达速率发请求，记录每条请求的 TTFT 与端到端时延。

### 6.1 轻载（4 req/s，32 条）

| k | 吞吐 tok/s | TTFT ms | E2E p99 ms |
|---|---|---|---|
| 1 | 33.39 | 55457.5 | 113771.8 |
| 2 | 61.92 | 27366.7 | 58525.1 |
| 4 | 112.38 | 12473.5 | 29105.5 |
| 8 | 186.82 | 5083.4 | 15134.9 |
| 16 | 268.26 | 1541.8 | 9615.0 |
| 32 | 308.92 | 170.5 | 9737.6 |

轻载下请求到达慢、系统不积压：k=32 吞吐最高（308.92）、TTFT 最低（0.17 s），
E2E p99 与 k=16 基本持平（9.74 s vs 9.62 s）。p99 的绝对值较大是因为 32 条请求
在 8 秒内陆续到达，时延里包含等待到达的时间；跨 k 比较时应看趋势而非绝对值。

### 6.2 过载（16 req/s，64 条）

| k | 吞吐 tok/s | TTFT ms | E2E p99 ms | 相对上一档 |
|---|---|---|---|---|
| 4 | 114.85 | 31938.1 | 67500.3 | — |
| 8 | 194.02 | 17616.7 | 38625.8 | +69% |
| 16 | 299.12 | 9971.6 | 24309.6 | +54% |
| 32 | 393.71 | 5894.3 | 18734.1 | +32% |

过载时系统持续积压：TTFT 始终在排队区（k=32 时仍有 5.9 s）。吞吐的边际增益随 k 递减
（+69% → +54% → +32%），k∈[1,32] 内未见饱和；外推饱和点接近 **FP16 的 KV 池并发上限 41.7×**
（若换 AWQ，上限提到 69×）。

> 口径注意：41.7× / 69× 来自启动日志 "4096 tokens per request" 的并发上限；
> 本实验每条请求约 640 token（512+128），KV 池实际能容纳的并发更高。
> 因此"饱和点≈41.7×"只能作量级参考，不能当精确饱和点。

### 6.3 结论

拐点只在**过载**下暴露，且位置取决于到达速率：

- 轻载：k=32 全面最优，没有权衡；
- 过载：提高 k 换吞吐，代价是排队时延；饱和点由 KV 池上限决定；
- 因此不存在一个固定的"单卡最优 `max_num_seqs`"，只能给出"配置—负载"二维结论。

## 7. 讨论

1. **与论文趋势一致，量级不同**：vLLM 论文报告 2–4×，本文 HF→vLLM 链条为 2.6×（batch=16），
   整体 3.3×，落在区间内；Orca 的 36.9× 来自 GPT-3 175B + request-level static batching 的
   巨大空转，本文的静态批只有 16 条，浪费小，增益自然小。
2. **量化的结论与 AWQ 论文看似相反，实则不同度量**：AWQ 的 >3× 是 TinyChat 专用 kernel 的
   token 吞吐；本文在 vLLM/Turing 上测到吞吐 −3.4%，但并发上限 +65%。在 vLLM 的部署语境下，
   量化应被当作"容量杠杆"，而不是"吞吐杠杆"。
3. **显存调参≈0 是负载相关结论**：batch=16、短序列下 KV 池不是瓶颈；换成更高并发或更长序列，
   E2-b 的曲线可能不同。这是本实验的边界，不能外推。
4. **方法学**：机制之间不正交，四项加总会误导；用"单变量消融 + 递进链条"两种视角更诚实。
   递进链条的两级负载条数不同，是系统级展示，不是严格方差分解。

## 8. 局限

- 单卡、合成负载、T4 较老（无 FlashAttention-2、无 4-bit 专用 kernel）；
- 未做 kernel 级优化，未评估 AWQ 的精度损失；
- **前缀共享不可测**（required 98304 > limit 65536），不能与其余机制并列比较；
- E3b 过载工况只跑了 1 次（无中位数），趋势可读但绝对值有抖动；
- E3b 的"饱和点 41.7×"是 4096-token 口径的 KV 池上限；本实验 640 token/请求，
  实际可容纳并发更高，该数字仅作量级参考；
- E1 与 E2-a 的请求条数不同（16 vs 32），递进链条不是严格单变量消融；
- vLLM 峰值显存为预分配占用，跨精度比较显存需求不可用；
- 使用 V0 引擎（`VLLM_USE_V1=0`），与新版引擎的调度/分页机制相同，但绝对性能可能不同；
- 未做 H800/A100 对照（sm80+ 才能测前缀共享）。

## 9. 结论

1. **单卡 decode 受带宽限制**：HF batch=1 实测 22.38 tok/s，约为理论上限 55 tok/s 的 41%；
   vLLM 32.99 tok/s 约为 60%。差距随并发扩大（1.5× → 2.6×），增益来自调度与显存管理。
2. **连续批处理是主贡献项**：固定 32 条请求，`max_num_seqs` 1→32 使吞吐从 27.69 涨到
   372.66 tok/s（13.5×）；显存调参≈0；Int4 量化吞吐 −3.4%，但把并发上限从 41.73× 提到 69.02×。
3. **最优点由负载决定**：轻载 k=32 全面最优；过载时边际增益递减，饱和点接近 FP16 并发上限 41.7×
   （AWQ 为 69×）。工程上应优先提高并发/启用连续批，量化作为容量杠杆，显存旋钮只在显存成为
   瓶颈时才调。
